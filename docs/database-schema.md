## 3. Conventions and reference integrity (PROPOSED)

The dictionary below is detailed design guidance, not executable DDL. `R` means required; `O` means nullable. Unless a row says global, every table has common fields: `id: UUID R` (generated by Team 5), `organization_id: external_id R`, `created_at: timestamptz R`. Mutable records also have `updated_at: timestamptz R` and `revision: bigint R >= 1` for optimistic concurrency. Append-only event/attempt/usage records omit update semantics except explicitly controlled state fields. UTC is stored; display timezone is a UI concern.

`external_id` means the owning team's opaque ID. UUID storage for these references is **ASSUMPTION pending Q02** because the ERDs suggest UUIDs while PDF examples use `ORG-001`, `EMP-001` and `PROJ-100`. Do not parse an ID to derive authority or tenant. Proposed contract wire type is string; database migration type must be ratified before production. Provider IDs are always opaque strings scoped by provider/connection/type/parent namespace. `user_id` is never inferred from an employee ID or email. Service principal IDs use a separate actor type.

- Add `UNIQUE (organization_id, id)` on tenant-owned parents. Every owned-child FK includes `organization_id`; querying by globally unique ID alone is forbidden. This prevents inserting or joining cross-tenant children.
- References to Teams 1-4 carry `owner_team`, `resource_type`, `resource_id` where polymorphic, and a verified tenant association from owner API. Polymorphic IDs cannot have a universal FK; allowlist types and validate each write/read.
- Global catalogs contain no tenant secrets, no usage, no permissions grants and no personal content. Only deployment-authorized operators can change them; tenant enablement is controlled by policy/configuration.
- JSONB is reserved for validated provider settings, schemas or minimized metadata. Define schema version and maximum sizes in code; no arbitrary configuration execution, raw SQL, shell, paths or client-selected endpoint URLs.
- Read/write APIs enforce tenant predicates and permissions independently of indexes. PostgreSQL row policies are a defense-in-depth option requiring Q03 and tests for pool-context reset, migrations and worker principals; they do not replace service checks.

## 5. State machines and transition invariants (PROPOSED)

| Record | States and legal flow | Invariant and recovery |
|---|---|---|
| Connection | pending -> active; active -> degraded; degraded -> active after verified recovery; active/degraded -> disabled; disabled -> active only after revalidation; any nonterminal -> disconnected | pending cannot sync; disabled cannot dispatch; disconnected revokes/unlinks credential and cancels pending work. Reconnect creates a new verified credential revision, with explicit decision whether same connection ID is reused. Revocation/revalidation is audited. |
| Sync job | queued -> running -> succeeded; running -> retry_wait -> running; queued/running/retry_wait -> cancelled; running/retry_wait -> failed | Lease generation guards stale worker writes; max attempts/deadline configurable. succeeded only after all intended canonical acknowledgments or explicitly documented accepted partial scope. Failed records remain inspectable and replay is a new authorized operation. |
| Inbox | received -> processing -> processed; received/processing -> ignored or failed | Signature verification precedes received. Duplicate same digest returns original receipt. Different digest for same key does not overwrite. Failed processing links retry job; payload expiry does not erase dedupe identity before approved replay horizon. |
| Agent run | queued -> running -> awaiting_approval -> running -> succeeded; queued/running/awaiting_approval -> cancelled or failed | Bounded steps/time/context/cost; pause never grants privilege. Resume rechecks caller/delegation, resource access, policy and tool status. |
| AI request/attempt | queued -> running -> succeeded/failed/unknown; request can be cancelled before dispatch | Unknown means provider completion/billing unconfirmed. Each retry creates a new attempt only when approved policy permits; response/accounting reconciled using provider request ID when possible. |
| Tool execution | pending -> awaiting_approval -> running -> succeeded/failed/unknown; pending/awaiting_approval -> cancelled; read-only permitted path pending -> running | Do not automatically resend an unknown write. Reconcile via provider operation ID/idempotency capability or operator review. Cancellation after dispatch is best effort and cannot claim external side effect was undone. |
| Approval binding | available -> consumed; available -> expired/revoked | Exact tenant/principal/tool version/arguments/resource revision/policy binding must match. Consumed is not reusable, even after crash. Unknown side effect requires reconciliation, not renewed approval replay. |
| Delivery | queued -> running -> acknowledged; running -> retry_wait -> running; exhausted -> failed | Duplicate consumer acknowledgment is safe. No exactly-once promise. Consumer-level deduplication and durable commit-before-ack required. |

## 6. Transactions, concurrency and failure boundaries

1. Connection creation validates tenant/permission/config, stores only a secret reference, and commits connection + audit/outbox intent in one Team 5 transaction. Secret creation and database commit are not atomic; use a staged secret reference and cleanup compensation on failure. Never mark active until credential verification succeeds.
2. Verify webhook using exact received bytes and provider rules; resolve the connection from trusted routing/installation metadata, never a caller-supplied tenant. Insert inbox + queued job in one transaction; acknowledge only after commit. A database outage yields retryable non-success. Payload parsing/normalization occurs after trust checks and bounded validation.
3. A worker leases a job using compare-and-set generation and short database transactions. Never hold a database transaction across a provider or cross-team HTTP call. The owning domain receives an idempotency key and returns a durable receipt; only then persist mapping/checkpoint/count. Crash after owner commit but before checkpoint causes duplicate delivery with the same key, not duplicate domain creation.
4. Before executing a tool, reauthorize exact resource scope and policy. Atomically consume valid approval binding and persist execution intent/audit/outbox. Send with a stable external idempotency key if supported. Crash after send is `unknown`; do not equate audit intent with successful external execution.
5. Each provider attempt records start and outcome independently of logical request. Append usage observation exactly once per measurement revision. Reconciliation may add a correction; derived reports select latest observation and separate unknown totals.
6. Approved deletion blocks new work first, revokes credentials, cancels jobs and purges retained content according to Q10. No cross-team cascading deletes. Preserve minimal audit/reference tombstones only if approved retention requires it; no undocumented indefinite retention.

## 7. Retention, deletion, privacy and data lifecycle

No source defines retention durations, storage regions or legal-hold rules. Q10 is a release blocker for real customer data. The defaults below are **PROPOSED behaviors**, not approved day counts.

| Data class | Proposed retention behavior | Required agreement |
|---|---|---|
| Credentials | Stored in selected secrets service; Team 5 DB has opaque reference/version only; revoke on disconnect, rotate without logging value | Q06/Q10: provider flow, secrets service, rotation, cleanup and access audit |
| Raw webhook/context/prompt/model/tool output | Minimize; raw retention off unless required/approved. If needed, encrypted restricted content reference with explicit expiry and access audit | Q10: classification, provider disclosure, residency and duration |
| External maps/checkpoints/dedupe keys | Retain for approved replay and reconciliation window; tombstone provider deletions; remove on tenant deletion subject to policy | Q04/Q10: delete semantics, replay horizon and mapping ownership |
| Audit | Append-only app permissions, bounded sanitized metadata, privileged read/export, controlled purge | Q10/Q14: duration, integrity/storage controls, backup expiry and audit-read audit |
| Usage | Metadata and estimated cost only; user deletion/pseudonymization must preserve approved aggregate accounting without unnecessary identity | Q07/Q10: cost reporting retention, correction and currency policy |
| Evaluation | Synthetic or approved redacted fixtures; immutable versions, access controlled, independently purged | Q12/Q10: corpus owner, expected result, privacy and retention |

Organization deactivation/deletion must arrive through authenticated CT-01 lifecycle semantics and be idempotent. If lifecycle delivery is unavailable, sensitive operations use current Team 1 validation rather than stale local assumption. Backup deletion and restored-data re-purge are part of Q14's recovery procedure, not solved by deleting primary rows alone.

## 8. Migration and verification plan

**PROPOSED:** Version migrations under Team 5 control; use SQLAlchemy/Alembic only after stack decision. Apply expand -> backfill/validate -> switch -> later contract. Review lock duration and backward compatibility. Deployment checks migration revision; production application startup does not race to execute migrations on every replica. Rollback normally redeploys a compatible application; destructive schema reversal is not a safe default. Restore drills must verify tenant data and event/job reconciliation.

Reviewers must verify: no Team 1-4 core table added; every tenant row/relation correctly scoped; external IDs remain opaque; all unique keys include correct provider namespace; JSON fields are bounded; secret samples absent; state transitions reject illegal changes; indexes match actual access paths; no approved record silently mutated; migrations can run on clean and previous schemas; constraints reject cross-tenant relationships; rollback/restore instructions preserve durable jobs and dedupe history. These checks support the requirement-specific tests in [implementation plan](implementation-plan.md).

Required database test cases include concurrent duplicate webhook insertion, same-key/different-body conflict, two workers acquiring one lease, stale worker checkpoint update, crash between domain acknowledgment and checkpoint, two actors consuming one approval, unknown tool outcome recovery, duplicate usage correction, mixed-currency aggregation rejection, tenant deletion with pending jobs, orphan logical reference quarantine, and restore followed by safe replay. Production approval requires agreed contracts and real integration evidence; a passing local fixture is insufficient.
